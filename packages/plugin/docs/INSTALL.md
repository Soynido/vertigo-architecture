## Endpoint credentials, one per seller

Each seller authenticates with their own token. The registry stores only SHA-256 digests; a raw token exists once,
in the operator's terminal, and nowhere else.

```
pnpm --filter @vertigo/harness run token list
pnpm --filter @vertigo/harness run token mint   p-CollaboratorBeta
pnpm --filter @vertigo/harness run token rotate p-valentin
pnpm --filter @vertigo/harness run token revoke p-CollaboratorAlpha
```

`--file` defaults to `HARNESS_HTTP_TOKENS_FILE`, and the command refuses a principal that `PRINCIPALS_FILE` does
not declare. The registry is replaced atomically and re-read on every request, so **mint, rotate and revoke take
effect on the next call, with no restart**; a rotation drops the previous token in the same write, leaving no
window in which both work.

**Where the token goes.** In the ChatGPT application's own authentication field, never in the server URL. The
server URL is then the bare endpoint (`https://<host>/mcp`), it carries no secret, and **one plugin archive serves
the whole team**. While `HARNESS_ALLOW_PATH_TOKEN` is still `true`, a URL of the form `https://<host>/mcp/<token>`
also works, but that URL *is* the credential: it cannot be shared, and its archive belongs to one person.

**If a token leaks** — pasted in a chat, a ticket or a screenshot — rotate it. That is the whole remediation:
`token rotate <principal>`, then put the new value in that person's application.
